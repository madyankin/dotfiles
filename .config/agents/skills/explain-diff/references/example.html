Let only the person approve MCP previews

Only a person can now create campaigns through MCP: creating or cancelling a preview takes a key that only the person’s interface receives. The agent can prepare campaigns but no longer approve them.

Look at in review6 risks · from reading the code
  1. The card’s key depends on the client. preview_card_key returns the key in a normal reply. It is marked app-only, but a client that ignores the mark lets the agent take the key and create campaigns without the person.
  2. One key for Create and Cancel. On the fallback path the key lands in the chat, and the agent could technically make the opposite decision. Separate keys would close this.
  3. Only the browser checks the card’s ticks. In the Claude Code dialog the server checks every tick itself. From the card it receives only the key, so the two paths give different guarantees.
  4. Campaigns are rebuilt at create time. The server rebuilds them from the agent’s input with current defaults and compares only the warnings. If a default changed within the 30 minutes, for example in the budget pool, the campaign is created differently from what the person saw.
  5. The preview may leave traces outside the database. inference The preview really saves the campaigns and rolls the transaction back. The rollback does not undo external calls or background jobs from model callbacks, if any; not checked.
  6. The session header never expires. Mcp-Session-Id is signed without an expiry. It grants no access, only tells the server which interface the client has; the worst case is the client getting the wrong path.
01

How the key reaches only the person

BeforeThere was no key. The preview returned JSON, and the agent decided when to call create.

AO-35520The preview of two campaigns gives the agent a table with the token, and gives the card the key as well.

The key is an HMAC of the preview token under the server secret: nothing needs to be stored, and the token alone cannot produce it. An MCP reply has three parts: text, data, and a hidden part called _meta. The client shows the model the text and the data and passes _meta only to the card, so that is where the server puts the key.

Step 1The key is derived from the token and compared in constant time models/change_request.rb:55
def approval_key
  OpenSSL::HMAC.hexdigest('SHA256', Rails.application.secret_key_base, "#{APPROVAL_KEY_PURPOSE}#{token}")
end

def approval_key_matches?(given_key)
  return false if given_key.blank?

  ActiveSupport::SecurityUtils.secure_compare(given_key, approval_key)
end

The agent knows the token, but without secret_key_base it cannot get the key.

Step 2The only place the key leaves the server server/preview_resource.rb:35
def self.result_meta(approval_key)
  tool_meta.merge(APPROVAL_KEY_META => approval_key)
end

If the client did not pass _meta to the card, the card asks preview_card_key for the key — an app-only tool the client hides from the model.

Proven by: change_requests_spec — the key only in _meta, preview_card_spec — no create or cancel without the key.

02

What the server checks before creating

BeforeThe server checked the token, the expiry and the 3-second wait, and created one campaign.

AO-35520Create with a valid key saves “Acme RT DE” and “Acme RT AT” in one transaction. A second identical call arriving at the same moment waits, then gets “token already used” — no duplicates.

create_campaign first locks the preview row in the database (SELECT … FOR UPDATE): until this call finishes, any other call with the same token waits. The server then checks that the preview is still open and the key is right, rebuilds the campaigns from the stored input and saves them all at once. If any one fails to save, or the warnings changed since the preview, everything rolls back.

If the preview had warnings, the call carries their fingerprint, warnings_digest. It tells the server the create relies on the same warnings the person saw.

Step 3The key is checked last server/change_requests.rb:124
def token_error(request, approval_key)
  return Responses.error('unknown token; preview again') unless request
  return already_used(request) if request.applied?
  return Responses.error('preview declined; preview again') if request.declined?
  return Responses.error('preview expired; preview again') if request.expired?

  not_approved unless request.approval_key_matches?(approval_key)
end

A repeat call after a successful create gets links to what was created, not “no key”. The old 3-second check is gone.

Proven by: change_requests_spec — apply without the key is refused, the token stays usable. Two concurrent calls are not tested.

03

How the card works

BeforeThere was no card. The agent retold the preview as text and waited for the person’s answer in the chat.

AO-35520The card “Create 2 campaigns” shows the shared fields once and the differences per campaign; after Create it says “Created 2 campaigns, paused.”

Claude Desktop, the Code tab and ChatGPT draw the preview as a card with Cancel and Create buttons. Create stays disabled until every warning is ticked. Normally the card calls create_campaign with the key itself.

Some clients do not let the card call tools. Then the card prepares a chat message, “Approve preview <token>, key <key>”. The person sends it like any other message, and the agent reads the key from it and calls create_campaign. The key reaches the agent only after the person has decided.

Not covered: the card’s behavior in the browser (bridge.js) — buttons, ticks, the fallback — has no specs. Server side: preview_card_spec.

04

How the Claude Code dialog works

BeforeThere was no dialog; the terminal client used the same text path as everyone else.

AO-35520The dialog shows a row per campaign and a tick box per warning; Accept with every box ticked creates both.

Claude Code in a terminal cannot draw the card, but it can show forms. The agent calls create_campaign without a key, and instead of an error the server asks the client to show an Accept / Decline dialog with the preview fields and a tick box for each warning. The client sends the person’s answer to the server itself, bypassing the agent.

Here the key never leaves the server: the server derives it from the token, as it did for the preview, and fills it in itself when Accept arrives. The agent cannot skip the dialog — without a key the create is refused, and an answer counts only for the preview whose token the client returns with it.

Step 4Accept counts only when every warning is ticked change_requests/dialog.rb:81
def warnings_ticked?(request, content)
  Preview::DialogForm.warning_keys(request.warnings.size).all? { |key| content[key] == true }
end

A client with neither a card nor forms gets “only the person can apply this preview”, and nothing is created.

Proven by: create_campaign_dialog_spec — Accept creates every campaign, an answer for another preview is refused.

05

How one preview covers many campaigns

BeforeOne preview meant one campaign, each approved separately.

preview_campaign now takes a campaigns array: up to 50 campaigns of one organization. All of them share one token, one card and one decision. Global experiments are still previewed one at a time; the shared code handles a list in both cases.

Step 5Save every campaign, even after the first failure server/change_requests.rb:197
def save_all(records)
  records.map(&:save).all?
end

all?(&:save) would stop at the first failure; map saves each one, so the error names every invalid campaign.

Example. AO-35520 with “Acme RT DE” and “Acme RT AT”. If the second is invalid, the first rolls back too and the preview stays open. Two campaigns with the same name raise a warning, not an error.

Proven by: change_requests_spec — “several campaigns in one preview”: one token, all or nothing, the 50 limit, one organization.

Other changes 6

What the card gets instead of a campaign’s JSON

The preview became one model shared by the card, the agent’s text and the dialog: fields are named and grouped by tab as in the Admin form, what all campaigns share is shown once, differences per campaign. The key is not in this data.

{ "title": "Create 2 campaigns",
  "ticket": "AO-35520",
  "shared":  [ { "tab": "Settings", "fields": [ ... ] } ],   // the same for all
  "differs": { "records": [ { "name": "Acme RT DE" }, { "name": "Acme RT AT" } ],
               "fields": [ ... ] },                         // how they differ
  "warnings": [ ... ],
  "token": "...", "apply_tool": "create_campaign" }

Trimmed example; the full field list is in preview/payload.rb.

What is stored in the database

mcp_change_requests gets two columns: results — which records the preview created, declined_at — when the person pressed Cancel. The status for preview_status is derived from them.

How the server knows the client draws the card

A client declares its capabilities once, when it connects, while requests arrive without state. The server hands the client a signed Mcp-Session-Id header with those capabilities and reads it on every request.

What goes into analytics

Mixpanel gets the person’s decision events, Preview Accept and Preview Decline, with the time from preview to decision and the number of campaigns.

Security around it

approval_key is filtered from logs. The local X-Dev-User sign-in no longer works through a tunnel: otherwise a public tunnel would let anyone sign in as any user.

What the agent is now told

Preview all campaigns of a ticket in one call; when the client draws the card, do not retell the preview and create nothing without the person’s key; after the decision, ask preview_status.
